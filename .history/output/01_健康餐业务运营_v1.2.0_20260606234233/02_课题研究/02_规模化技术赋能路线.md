# 规模化技术赋能路线

> 日期：2026-06-06
> 类型：技术产品路线 / 规模化系统设计

---

## 背景修正

上一份文档建议“可以先用飞书多维表格、Notion、Airtable、Excel 加自动化”作为低成本起步方式。这个建议适合非技术团队快速止血，但不完全适合当前用户身份。

用户明确补充：老婆自己能处理飞书或 Excel，用户作为技术角色，希望一步到位为规模化做赋能准备。

因此，本轮判断调整为：

- 不以表格为主方案。
- 不先做大而全客户小程序。
- 应该建设一个“内部交易核心 + 运营中台 + 自动化接口”的可扩展系统。
- 第一个版本面向内部运营人员使用，但数据模型、权限、接口、状态机和自动化能力从第一天按规模化设计。

---

## 一句话结论

你要做的不是“记账工具”，也不是“客户点餐页”，而是健康餐转单业务的交易操作系统。第一版可以只给内部用，但它必须从第一天就拥有订单核心、账务核心、履约核心、客户核心和自动化接口。

---

## 技术赋能的核心原则

### 1. 一步到位不是一次性做完所有功能

“一步到位”应该理解为：底层模型和架构方向一次选对，功能按阶段释放。

错误的一步到位：

- 一上来做客户小程序、供应商后台、骑手端、营销 CRM、财务系统。
- 每个模块都只做一点，最后没有一个模块稳定可用。
- 业务规则未稳定前，把流程写死在代码里。

正确的一步到位：

- 先定义交易核心数据模型。
- 先建立状态机和审计日志。
- 先把订单、收款、预付款、履约串起来。
- 先让内部运营效率提升，并沉淀真实业务数据。
- 后续客户自助、供应商协同、配送优化都复用同一套核心数据。

### 2. 先做系统真相源，再做外部入口

当前小红书和微信仍然可以作为获客与沟通入口。技术系统的第一使命不是替代微信，而是接管微信背后的交易事实：

- 客户事实。
- 订单事实。
- 收款事实。
- 预付款余额事实。
- 供应商履约事实。
- 成本和毛利事实。

只要这些事实进入系统，微信只是沟通界面，不再是业务数据库。

### 3. 业务流程必须事件化

健康餐转单业务看似简单，但实际包含多个事件：

- 客户咨询。
- 运营报价。
- 客户付款。
- 生成订单。
- 核销预付款。
- 下发供应商。
- 供应商确认。
- 配送完成。
- 售后退款。
- 客户复购。

这些动作应该作为事件写入系统，而不是只改一个最终状态。事件化的好处是后续能做自动化、复盘、责任追踪和数据分析。

## 建议建设的系统形态

### 产品形态

第一版建议做一个 Web 运营中台，不做移动端优先。

原因：

- 内部录单、对账、查单、批量下单更适合桌面 Web。
- 你作为技术可以快速迭代业务规则。
- 后续客户自助页、供应商确认页、配送端页面都可以作为轻量外部页面接入。

建议系统名称可以暂定为：

```text
健康餐交易运营中台
```

### 角色边界

第一阶段只需要 3 类角色：

| 角色 | 能力 |
|---|---|
| 运营 | 录客户、建订单、确认收款、生成供应商下单、处理售后 |
| 管理员 | 配置套餐、价格、供应商成本、配送规则、查看经营数据 |
| 供应商访问页 | 查看今日订单、确认接单、反馈异常 |

客户角色可以后置。客户自助下单不是第一阶段刚需，但系统要预留客户下单 API。

## 核心领域模型

### 1. 客户域

客户不是微信昵称，而是可复购的业务主体。

核心实体：

- Customer：客户。
- CustomerContact：联系方式，如微信、小红书、手机号。
- CustomerAddress：配送地址。
- CustomerPreference：忌口、口味、目标、备注。
- CustomerTag：减脂、控糖、增肌、宝妈、上班族等标签。

关键点：

- 微信名会变，小红书昵称也会变，所以必须有系统客户 ID。
- 地址、忌口和偏好要独立出来，避免每次重新问。
- 后续复购、预付款、售后都挂在同一个客户 ID 上。

### 2. 订单域

订单是系统主轴。

核心实体：

- Order：订单头。
- OrderItem：订单明细。
- OrderStatusLog：订单状态日志。
- OrderCost：订单成本拆分。
- OrderNote：订单备注和运营记录。

建议订单状态：

```text
DRAFT 草稿
WAIT_PAY 待付款
PAID 已付款
TO_SUPPLIER 待下发供应商
SUPPLIER_CONFIRMED 供应商已确认
DELIVERING 配送中
COMPLETED 已完成
AFTER_SALE 售后中
REFUNDED 已退款
CANCELED 已取消
```

关键点：

- 状态改变必须写日志，记录谁在什么时候因为什么改了状态。
- 一笔订单可以有多个餐品或多个配送日，但第一版可以先限制为“一单一日一餐”，降低复杂度。
- 多日套餐不要一开始做成一个模糊订单，应该拆成多笔待履约订单，预付款账户统一核销。

### 3. 支付与账务域

这是你现在最糊、也最值得技术介入的地方。

核心实体：

- Payment：收款记录。
- PaymentAllocation：收款分摊，表示一笔钱对应哪些订单或预付款账户。
- PrepaidAccount：客户预付款账户。
- PrepaidLedger：预付款流水。
- Refund：退款记录。
- ReconciliationIssue：对账异常。

关键规则：

- 收到钱不等于营业额。
- 预付款充值不等于已确认收入。
- 预付款每核销一餐，才转成对应订单收入。
- 每笔收款必须要么关联订单，要么进入预付款账户，要么标记为异常。

建议账务分类：

```text
ORDER_PAYMENT 订单收款
PREPAID_TOPUP 预付款充值
BALANCE_DEDUCTION 余额核销
REFUND 退款
ADJUSTMENT 调账
UNKNOWN 异常待确认
```

### 4. 供应商履约域

供应商不是微信接单对象，而是履约能力单元。

核心实体：

- Supplier：供应商。
- SupplierProduct：供应商可供餐品。
- SupplierOrderBatch：供应商下单批次。
- SupplierOrderItem：供应商下单明细。
- SupplierConfirmation：供应商确认记录。
- SupplierException：供应商异常。

关键点：

- 运营不应把微信聊天拼给供应商，而应由系统按供应商、日期、餐型生成批次。
- 每个批次要有“已生成、已发送、已确认、异常”的状态。
- 后续压供应商成本靠的就是这些批次数据和稳定单量。

### 5. 配送域

第一阶段可以先记录配送成本，不一定自建配送调度。

核心实体：

- DeliveryTask：配送任务。
- DeliveryArea：配送区域。
- DeliveryCostRule：配送成本规则。
- DeliveryStatusLog：配送状态日志。

关键点：

- 即使配送外包，也要记录每单配送成本。
- 地址区域要逐步结构化，后续才知道哪些区域有配送密度。
- 未来压配送成本，靠的是区域密度、时段集中和稳定波次。

## 第一版系统模块

### 模块 1：线索与客户录入

目标：从小红书和微信来的客户不再丢。

功能：

- 创建客户。
- 记录来源：小红书笔记、私信、微信好友、老客推荐。
- 录入微信名、小红书 ID、手机号、地址、忌口。
- 客户状态流转：新咨询、已报价、待付款、已成交、履约中、可复购、流失。
- 客户时间线：咨询、报价、付款、订单、售后都能回看。

### 模块 2：订单工作台

目标：每笔订单都能被看见、推进和追踪。

功能：

- 建订单。
- 选择客户、日期、餐品、套餐、配送地址。
- 自动计算售价、供应商成本、配送成本和毛利。
- 标记订单状态。
- 今日待办：待付款、待下发供应商、待供应商确认、待配送、售后异常。

### 模块 3：收款与预付款

目标：把钱和单绑定。

功能：

- 录入收款。
- 收款关联订单。
- 收款转入预付款账户。
- 预付款核销订单。
- 退款记录。
- 异常收款池。
- 客户余额查询。

### 模块 4：供应商批量下单

目标：把手工转发变成系统生成。

功能：

- 按日期和供应商生成下单批次。
- 一键生成微信可复制文本。
- 供应商确认状态。
- 下单批次和订单反向关联。
- 异常标记：缺餐、地址问题、备注冲突。

第一版可以先“一键复制文本”，不必直接接微信接口。这样开发成本低，但核心数据已经进入系统。

### 模块 5：经营仪表盘

目标：每天知道赚不赚钱、乱在哪里。

功能：

- 今日订单数。
- 今日实收金额。
- 今日确认营业额。
- 今日预收款。
- 今日预付款核销金额。
- 今日供应商成本。
- 今日配送成本。
- 今日毛利。
- 异常订单数。
- 未关联收款数。

## 技术架构建议

### 推荐架构

第一阶段建议使用单体应用，但领域边界要清楚。

```text
Web 前端
  ↓
后端 API
  ↓
业务服务层
  ├─ 客户服务
  ├─ 订单服务
  ├─ 支付账务服务
  ├─ 供应商履约服务
  ├─ 配送服务
  └─ 经营报表服务
  ↓
PostgreSQL
  ↓
事件日志 / 审计日志 / 定时任务
```

不建议一开始微服务。订单量和团队规模还没到，微服务只会制造运维负担。

### 技术栈建议

如果你想快速做出可用系统：

| 层 | 建议 |
|---|---|
| 前端 | Next.js / React |
| 后端 | Next.js API、NestJS 或 FastAPI |
| 数据库 | PostgreSQL |
| ORM | Prisma / SQLAlchemy |
| UI | shadcn/ui 或 Ant Design |
| 部署 | Vercel + Supabase / Railway / 自建云服务器 |
| 定时任务 | pg_cron、云函数、队列任务 |

如果你更看重长期工程控制，可以选：

```text
Next.js 前端 + NestJS 后端 + PostgreSQL + Prisma
```

理由：

- 前后端分层清晰。
- NestJS 对领域模块、权限、队列和后台任务更友好。
- PostgreSQL 足够承载订单、账务、事件日志和报表。

### 数据库第一原则

第一版系统最重要的是数据库设计，而不是页面好不好看。

必须从第一天做好：

- 主键 ID。
- 创建时间和更新时间。
- 操作人。
- 状态日志。
- 账务流水。
- 软删除或取消原因。
- 审计日志。

否则后面业务一复杂，就会回到“账又糊了”的老问题。

## 自动化能力路线

### 第 1 阶段：复制型自动化

系统生成内容，人复制到微信。

- 供应商下单文本。
- 客户付款提醒。
- 地址确认文本。
- 配送提醒文本。
- 售后处理文本。

这一步最稳，不依赖微信接口。

### 第 2 阶段：提醒型自动化

系统提醒运营该做什么。

- 待付款超过 2 小时提醒。
- 今日已付款未下发供应商提醒。
- 供应商未确认提醒。
- 客户余额不足提醒。
- 负毛利订单提醒。

### 第 3 阶段：半集成自动化

接入可控外部渠道，但保留人工确认。

- 微信收款截图上传识别。
- 小红书线索手动导入。
- 支付记录自动匹配。
- 供应商确认链接。
- 客户轻量下单表单。

### 第 4 阶段：规模化协同

当订单量稳定后，再做外部协同端：

- 客户自助下单页。
- 客户余额查询页。
- 供应商接单页。
- 配送任务页。
- 数据看板和成本谈判报表。

## MVP 范围建议

### 必须做

- 登录和角色权限。
- 客户管理。
- 订单管理。
- 收款记录。
- 预付款账户和核销。
- 供应商批量下单文本生成。
- 今日待办。
- 每日经营数据。
- 状态日志和账务流水。

### 可以后置

- 客户小程序。
- 在线支付接口。
- 微信自动发消息。
- 小红书自动抓线索。
- 供应商完整后台。
- 配送路径优化。
- 复杂营销 CRM。

### 坚决不要第一版做

- 多城市多门店复杂架构。
- 微服务。
- 完整财务会计系统。
- 全自动微信机器人。
- 精细化权限到字段级。
- 大屏式 BI。

## 你作为技术的核心价值

如果只是做表格，你的技术优势没有被释放。你真正能做的是：

- 把业务从聊天记录里抽象成领域模型。
- 把状态流转做成系统约束，减少人为遗漏。
- 把账务流水和订单核销绑定，避免越做越糊。
- 把供应商下单批次化，为后续压成本提供数据。
- 把每个动作沉淀成事件，为自动化和分析打底。
- 把内部运营系统逐步外化成客户端、供应商端和配送端。

## 30 天技术路线

### 第 1 周：交易核心

目标：订单、客户、收款、预付款能跑通。

交付：

- 数据库 schema。
- 客户 CRUD。
- 订单 CRUD。
- 收款 CRUD。
- 预付款充值和核销。
- 订单状态流转。

### 第 2 周：履约与对账

目标：能处理每天真实订单。

交付：

- 供应商批次生成。
- 下单文本生成。
- 今日待办。
- 对账异常池。
- 毛利计算。
- 操作日志。

### 第 3 周：经营视图

目标：能指导经营动作。

交付：

- 日经营看板。
- 客户转化漏斗。
- 套餐毛利分析。
- 供应商成本分析。
- 配送区域成本分析。

### 第 4 周：外部协同雏形

目标：开始减少微信中反复沟通。

交付：

- 客户确认页或轻量下单页。
- 供应商确认页。
- 客户余额查询页。
- 运营话术模板生成。

## 与上一版建议的关系

飞书或 Excel 可以作为老婆临时整理运营信息的工具，但不应作为你的技术主线。

你的技术主线应该是：

```text
内部运营中台
→ 交易核心稳定
→ 履约和账务自动化
→ 经营数据沉淀
→ 客户自助与供应商协同
→ 基于数据压供应商和配送成本
```

也就是说，表格能解决“今天别乱”，系统要解决“以后能放大”。

---

## 最终判断

你现在应该做一个可规模化的内部交易运营系统。第一版不要贪外部入口，但底层必须按未来规模化来设计。

最值得立刻开工的是：

- 订单核心。
- 支付与预付款核心。
- 供应商履约批次。
- 今日待办。
- 每日经营看板。

这些能力一旦跑通，你们就不只是“接单转单”，而是在形成一个可复制的健康餐交易网络。后续无论是做客户自助、供应商压价、配送优化，还是扩区域，都有技术底座可以承接。
