# 客户付款解决方案

> 日期：2026-06-07
> 类型：问题答疑 / 支付与账务流程

---

## 问题

用户问：客户付款怎么解决？

这个问题不能只理解成“客户用微信还是支付宝付”。真正要解决的是：

```text
客户怎么方便付款，系统怎么知道这笔钱是谁付的、为了哪一单付的、是否属于预付款、是否已经核销、是否需要退款。
```

付款入口只是表层，账务归属才是核心。

---

## 一句话结论

第一版不要急着接复杂支付接口。建议先做“系统生成应收款单 + 运营发送收款说明 + 客户付款 + 运营确认入账 + 系统自动关联订单/预付款”的半自动流程。

等订单流程稳定后，再接微信支付或支付宝的官方商户支付能力，让支付结果自动回调系统。

---

## 客户付款要拆成两层

### 第 1 层：客户实际怎么把钱付过来

可选方式：

- 微信转账。
- 微信收款码。
- 支付宝收款码。
- 商户收款码。
- 后期微信支付/支付宝支付链接或二维码。

### 第 2 层：系统怎么处理这笔钱

系统必须回答：

- 谁付的？
- 付了多少？
- 什么时候付的？
- 是订单款还是预付款？
- 关联哪笔订单？
- 如果是预付款，进入哪个客户余额账户？
- 是否已经核销？
- 是否有退款？
- 是否异常待确认？

如果第 2 层没做好，即使用了微信支付或支付宝，也只是“收款更方便”，账仍然可能糊。

---

## 第一版推荐做法：付款请求单

系统里新增一个概念：

```text
付款请求单
```

它不是最终收款记录，而是“系统向客户发起的一次应收款请求”。

### 付款请求单字段

建议字段：

| 字段 | 说明 |
|---|---|
| 付款请求 ID | 系统生成，例如 PR20260607-001 |
| 客户 ID | 谁要付款 |
| 关联订单 ID | 如果是订单款，关联具体订单 |
| 类型 | 订单付款 / 预付款充值 / 补差价 |
| 应付金额 | 客户应付多少钱 |
| 已付金额 | 实际收到多少钱 |
| 状态 | 待发送 / 待付款 / 已付款 / 部分付款 / 已取消 / 已过期 |
| 收款方式 | 微信 / 支付宝 / 商户码 / 其他 |
| 备注 | 客户备注、运营备注 |
| 创建时间 | 何时创建 |
| 确认时间 | 何时确认收到 |

### 为什么需要付款请求单

因为它能把付款从聊天里拉回系统。

没有付款请求单时：

```text
运营报价 → 客户随手转账 → 运营晚上想这是谁的钱
```

有付款请求单后：

```text
系统生成应收款 → 客户按请求付款 → 运营或系统确认 → 钱自动归属
```

## 第一版客户付款流程

### 场景 1：客户买单餐

操作流程：

```text
运营创建订单
  ↓
系统生成付款请求单
  ↓
运营复制付款说明发微信
  ↓
客户付款
  ↓
运营在系统点击“确认收款”
  ↓
系统创建收款记录
  ↓
收款关联订单
  ↓
订单状态变为“已付款待下单”
```

运营看到的操作：

1. 在订单详情点击“发起收款”。
2. 系统生成付款说明：

```text
【健康餐付款】
订单号：O20260607-001
客户：张三
餐品：减脂午餐 A
金额：38 元
请转账后备注：0707-001
```

3. 运营复制给客户。
4. 客户付款。
5. 运营确认收到后，点击“确认收款”。
6. 系统自动把订单改为“已付款待下单”。

系统自动做的事：

- 创建付款请求。
- 创建收款记录。
- 将收款分配到订单。
- 写订单付款日志。
- 生成待下发供应商任务。

---

### 场景 2：客户充值预付款

操作流程：

```text
运营在客户详情发起预付款充值
  ↓
系统生成充值付款请求
  ↓
客户付款
  ↓
运营确认收款
  ↓
系统增加客户余额
  ↓
写入预付款流水
```

运营看到的操作：

1. 打开客户详情。
2. 点击“充值预付款”。
3. 输入金额，例如 300 元。
4. 系统生成付款说明：

```text
【健康餐预付款充值】
客户：张三
充值金额：300 元
请转账后备注：C001-充值
```

5. 客户付款后，运营点击“确认收款”。

系统自动做的事：

- 创建收款记录。
- 标记类型为“预付款充值”。
- 增加客户余额。
- 写入 `prepaid_ledger`。
- 不把 300 元全部计为当日营业额，只计为预收款。

关键点：

```text
预付款充值不是营业额，只有后续核销到具体订单时才转成订单收入。
```

---

### 场景 3：客户用余额下单

操作流程：

```text
运营创建订单
  ↓
选择“余额支付”
  ↓
系统检查余额是否足够
  ↓
自动扣减余额
  ↓
写入预付款核销流水
  ↓
订单变为已付款
```

系统自动做的事：

- 检查客户余额。
- 扣减订单金额。
- 写入核销流水。
- 更新客户剩余余额。
- 将订单收入计入营业额。
- 订单进入“待下发供应商”。

示例：

```text
客户余额：300 元
订单金额：38 元
核销后余额：262 元
本单营业额：38 元
```

---

### 场景 4：客户补差价

触发场景：

- 客户余额不足。
- 客户临时加餐。
- 配送费变更。
- 套餐升级。

操作流程：

```text
系统发现应付金额 > 可用余额/已付款金额
  ↓
生成补差价付款请求
  ↓
客户补款
  ↓
运营确认
  ↓
系统补齐订单付款状态
```

系统价值：

- 不会出现“客户到底还差几块钱”的混乱。
- 补款和原订单能关联起来。

---

### 场景 5：退款

触发场景：

- 客户取消订单。
- 餐品/配送出问题。
- 预付款余额退还。

操作流程：

```text
运营进入订单或客户余额
  ↓
点击“发起退款”
  ↓
选择退款类型
  ↓
输入退款金额和原因
  ↓
实际退款给客户
  ↓
系统记录退款
  ↓
影响订单毛利或预付款余额
```

退款类型：

- 订单退款。
- 预付款余额退款。
- 售后补偿。

系统要记录：

- 退款金额。
- 退款原因。
- 关联订单或预付款账户。
- 操作人。
- 退款时间。

## 第一版不要急着全自动支付

第一版建议先做到：

```text
系统生成应收款
运营发送付款说明
客户微信/支付宝付款
运营确认收款
系统自动归账
```

这样最快，且能验证：

- 订单和付款是否能对上。
- 预付款核销是否清楚。
- 运营是否真的省时间。
- 每日复盘是否能跑通。

不建议第一版就做：

- 微信支付全接口。
- 支付宝全接口。
- 自动分账。
- 多支付渠道聚合。
- 自动识别所有收款截图。

这些可以后置。

---

## 第二阶段：商户收款码 + 对账导入

当日订单稍微多一点后，可以升级为：

```text
商户收款码
  ↓
系统仍生成付款请求单
  ↓
客户付款时备注订单号/客户号
  ↓
运营导入或核对收款流水
  ↓
系统按金额、时间、备注匹配付款请求
```

这一步比纯手工更稳，但还不用完整接支付 API。

适合情况：

- 每天十几单到几十单。
- 人工确认开始费时。
- 但还没必要做完整支付接口。

---

## 第三阶段：接微信支付或支付宝官方接口

当订单量稳定、业务要客户自助付款时，再接官方支付能力。

### 接入后流程

```text
系统创建订单/充值请求
  ↓
系统调用支付平台生成支付二维码或支付链接
  ↓
客户支付
  ↓
支付平台回调系统
  ↓
系统自动标记已付款
  ↓
自动关联订单或预付款账户
```

系统需要处理：

- 支付请求创建。
- 支付回调验签。
- 幂等处理。
- 支付状态同步。
- 退款接口。
- 对账单导入或自动对账。

### 支付方式选择

如果客户仍然主要在微信里沟通：

- 早期可以继续微信转账/收款码。
- 后期可考虑微信支付商户能力。

如果做网页或小程序：

- 微信内页面通常考虑微信支付相关能力。
- 普通网页也可以考虑支付宝或微信二维码支付。

具体接入方式要根据最终产品形态决定：

- 微信公众号/小程序内支付。
- Web 页面二维码支付。
- 支付宝网页支付。

## 系统里需要哪些支付相关表

建议最少有这些：

```text
payment_requests
payments
payment_allocations
prepaid_accounts
prepaid_ledger
refunds
reconciliation_issues
```

### payment_requests：付款请求

表示“应该收多少钱”。

### payments：实际收款

表示“实际收到了多少钱”。

### payment_allocations：收款分配

表示“这笔钱分配到哪笔订单或预付款账户”。

### prepaid_accounts：客户余额账户

表示“客户当前还有多少预付款余额”。

### prepaid_ledger：预付款流水

表示“每一次充值、扣减、退款、调整”。

### refunds：退款

表示“退了多少钱、为什么退、关联哪笔订单或余额账户”。

### reconciliation_issues：对账异常

表示“系统不知道这笔钱归哪里，需要人工处理”。

## 付款状态设计

### 付款请求状态

```text
CREATED 已创建
SENT 已发送给客户
WAIT_PAY 待付款
PAID 已付款
PARTIAL 部分付款
CANCELED 已取消
EXPIRED 已过期
```

### 订单付款状态

```text
UNPAID 未付款
PARTIAL 部分付款
PAID 已付款
REFUNDED 已退款
```

### 收款匹配状态

```text
UNMATCHED 未匹配
MATCHED 已匹配
ALLOCATED 已分配
REFUNDED 已退款
```

## 每日对账怎么做

每天晚上，系统应该展示：

- 今日应收。
- 今日实收。
- 今日订单收入。
- 今日预付款充值。
- 今日预付款核销。
- 今日退款。
- 未匹配收款。
- 部分付款订单。
- 负毛利订单。

运营只需要处理异常：

```text
哪些钱没关联？
哪些订单没付清？
哪些预付款余额异常？
哪些退款影响了毛利？
```

这比“今天收了多少钱”有用得多。

## 付款方案推荐路线

### 第 1 步：半自动收款

先做：

- 付款请求单。
- 手动确认收款。
- 订单款/预付款分类。
- 预付款余额与流水。
- 退款记录。
- 每日对账异常。

目标：

```text
不再账糊。
```

### 第 2 步：商户码与流水匹配

再做：

- 商户收款码。
- 客户付款备注订单号。
- 收款流水导入或人工匹配。
- 异常池。

目标：

```text
减少人工确认成本。
```

### 第 3 步：官方支付接口

最后做：

- 微信支付/支付宝支付。
- 支付链接或二维码。
- 支付回调。
- 自动确认。
- 自动对账。
- 接口退款。

目标：

```text
客户自助付款，系统自动入账。
```

## 关键提醒

### 1. 不要让客户随便转账

每次付款前，最好由系统生成付款请求，带上订单号或客户号。否则后面还是难对账。

### 2. 预付款一定要有余额流水

只记录“客户还有 262 元”不够，必须知道这个余额怎么来的、怎么扣的、有没有退过。

### 3. 不要把预付款全部算成营业额

预付款是预收款，核销到具体订单后，才对应营业额。

### 4. 不要为了支付接口拖慢 MVP

第一版最重要的是付款归账逻辑，而不是接哪个支付平台。

### 5. 商户主体、税务、预付款规则要后续合规确认

如果业务逐渐规模化，商户主体、发票、退款规则、预付款说明等需要找会计或法律专业人士确认。系统侧可以先把流水和规则记录清楚。

---

## 最终结论

客户付款的第一版解决方案是：

```text
系统发起付款请求
  ↓
客户通过微信/支付宝/商户码付款
  ↓
运营确认收到
  ↓
系统创建收款记录
  ↓
系统把钱分配到订单或预付款账户
  ↓
订单进入待下单，或客户余额增加
  ↓
每日对账检查异常
```

也就是说，系统先解决“钱和单怎么对上”。支付方式可以先手动，后面再逐步接官方支付接口。
