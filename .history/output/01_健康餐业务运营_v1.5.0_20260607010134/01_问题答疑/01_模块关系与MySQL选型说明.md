# 模块关系与 MySQL 选型说明

> 日期：2026-06-06
> 类型：问题答疑 / 技术架构澄清

---

## 问题

用户追问：

1. 前面提到的客户域、订单域、支付账务域、供应商履约域、配送域，这些模块是否相互独立？
2. 用户已有阿里云 MySQL，希望使用现成资源，不单独引入 PostgreSQL。

---

## 简短回答

这些模块不是相互独立的应用，也不建议第一版拆成微服务。它们应该是同一个交易运营中台里的不同领域模块：代码上分清边界，数据上围绕同一套订单和账务真相源协作。

数据库可以直接用阿里云 MySQL。当前业务阶段没有必要为了 PostgreSQL 单独增加一套数据库资源。更重要的是把表结构、事务边界、状态日志、账务流水和索引设计做好。

---

## 模块之间是什么关系

### 1. 它们不是独立系统，而是领域边界

建议第一版采用“模块化单体”：

```text
一个 Web 运营中台
一个后端应用
一个阿里云 MySQL 数据库
多个清晰的业务模块
```

也就是说：

- 客户模块不独立部署。
- 订单模块不独立部署。
- 支付账务模块不独立部署。
- 供应商履约模块不独立部署。
- 配送模块不独立部署。

它们在代码里分模块，在业务上各司其职，但运行时属于同一个系统。

### 2. 模块之间有主从关系

推荐主轴是订单。

```text
客户
  ↓
订单
  ↓
支付/预付款核销
  ↓
供应商履约批次
  ↓
配送记录
  ↓
经营看板
```

每个模块的职责不同：

| 模块 | 主要职责 | 依赖关系 |
|---|---|---|
| 客户模块 | 管理客户身份、联系方式、地址、偏好 | 被订单、收款、预付款引用 |
| 订单模块 | 承载交易主线、状态流转、成本和毛利 | 依赖客户，驱动支付、履约、配送 |
| 支付账务模块 | 管理收款、预付款、核销、退款、对账异常 | 依赖客户和订单 |
| 供应商履约模块 | 将订单批量生成供应商下单批次 | 依赖已付款或待履约订单 |
| 配送模块 | 记录配送任务、配送成本、配送状态 | 依赖订单和供应商履约结果 |
| 经营看板 | 展示收入、预收款、毛利、异常 | 读取所有核心模块数据 |

所以它们不是“互不相干”，而是“强业务关联、清晰代码边界”。

---

## 为什么第一版不拆微服务

当前不建议拆微服务，原因很直接：

- 团队人数少，微服务会增加部署、监控、日志、链路追踪和数据一致性成本。
- 当前最复杂的不是高并发，而是业务规则和账务关系。
- 订单、收款、预付款核销、供应商下单经常需要同一个事务或强一致读写。
- 第一版拆微服务，很容易把简单交易流程拆成跨服务对账问题。

更好的做法是：

```text
模块化单体
→ 领域边界清楚
→ 表结构稳定
→ 事件日志完整
→ 订单量和团队规模上来后再考虑拆分
```

---

## 阿里云 MySQL 是否可以承载

可以，而且当前阶段非常合适。

健康餐转单业务第一阶段的数据特点是：

- 订单量不会立刻大到需要复杂分布式数据库。
- 需要可靠事务。
- 需要订单、收款、预付款核销之间的一致性。
- 需要常规报表和筛选。
- 需要低成本、稳定、易维护。

阿里云 MySQL 足够覆盖这些需求。

## 使用 MySQL 时要注意什么

### 1. 使用 InnoDB

所有核心业务表必须使用 InnoDB，保证事务、行锁和外键能力。

### 2. 金额字段不要用 float

金额统一用：

```text
DECIMAL(10,2)
```

或根据业务扩大到：

```text
DECIMAL(12,2)
```

不要用 `FLOAT` 或 `DOUBLE` 存钱。

### 3. 状态字段建议用 varchar

订单状态、支付类型、账务类型可以先用 `VARCHAR`，例如：

```text
WAIT_PAY
PAID
COMPLETED
PREPAID_TOPUP
BALANCE_DEDUCTION
```

不建议第一版强依赖 MySQL `ENUM`，因为业务状态早期可能频繁调整。

### 4. 每张核心表都要有审计字段

建议统一字段：

```text
id
created_at
updated_at
created_by
updated_by
deleted_at
```

如果第一版只有你和你老婆使用，`created_by` / `updated_by` 也可以先保留字段，后续再真正接权限。

### 5. 核心动作写日志表

不要只更新订单最终状态，要写状态日志：

```text
order_status_logs
prepaid_ledger
operation_logs
```

这样以后账务、售后、供应商异常都能追溯。

### 6. 关键查询建索引

第一版至少要考虑：

- `orders.customer_id`
- `orders.status`
- `orders.service_date`
- `payments.customer_id`
- `payment_allocations.order_id`
- `prepaid_ledger.customer_id`
- `supplier_order_batches.supplier_id`
- `supplier_order_batches.service_date`

这些索引会直接影响今日待办、客户详情、对账和供应商批次。

## 技术栈修正

基于用户已有阿里云 MySQL，推荐技术栈修正为：

```text
Next.js 前端
NestJS 后端
阿里云 MySQL
Prisma ORM
Redis 可选
阿里云 OSS 可选
```

其中：

- MySQL 承载核心交易数据。
- Prisma 负责 schema、迁移和类型安全查询。
- Redis 暂时不是必需，只在后续做缓存、任务队列或验证码时再用。
- OSS 可用于存收款截图、客户凭证、供应商确认截图等附件。

## 推荐代码结构

第一版后端可以这样分模块：

```text
src/
  modules/
    customers/
    orders/
    payments/
    prepaid/
    suppliers/
    fulfillment/
    delivery/
    dashboard/
    auth/
    audit/
```

模块分开，但可以共用同一个数据库连接和事务管理。

订单创建、收款分摊、预付款核销这类动作，建议在服务层显式控制事务：

```text
创建订单
→ 写订单主表
→ 写订单明细
→ 写订单状态日志
→ 如有预付款核销，写 prepaid_ledger
→ 写 operation_logs
```

---

## 结论

模块不应相互独立成多个系统，而应在一个模块化单体里协同工作。客户是基础，订单是主轴，支付账务保证钱清楚，供应商履约保证单能交付，配送记录保证成本可分析，经营看板负责把这些数据变成决策。

数据库直接使用阿里云 MySQL 是合理选择。当前真正需要小心的不是 MySQL 能不能撑住，而是从第一版开始就把事务、金额精度、状态日志、预付款流水和索引设计好。
