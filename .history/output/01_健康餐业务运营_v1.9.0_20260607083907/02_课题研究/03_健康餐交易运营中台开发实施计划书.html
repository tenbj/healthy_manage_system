健康餐业务运营 · 开发实施计划书

健康餐交易运营中台从 0 到 MVP 的可执行计划

本文档用于指导任意 AI 或开发者接手实施：先做可运行原型，再做模块化单体后端，使用阿里云 MySQL，优先跑通客户、订单、付款、供应商批次和每日复盘主链路。

版本 v1.0 计划周期 4-6 周 MVP 优先 最后更新 2026-06-07

1. 目标与边界

业务目标

让健康餐转单业务从微信和人脑驱动，变成系统驱动。第一版重点解决账糊、漏单、重复操作、供应商确认和每日复盘。

系统目标

建设一个内部 Web 运营中台，先服务运营人员，后续再开放客户确认页、余额查询页和供应商确认页。

技术目标

采用模块化单体：Next.js/React 前端、NestJS 后端、阿里云 MySQL、Prisma ORM。第一版不拆微服务。

第一版主链路： 新建客户 → 报价/待付款 → 记录收款 → 创建订单 → 生成供应商批次 → 供应商确认 → 订单完成/售后 → 每日复盘。

明确不做

暂不做 原因 后置条件
完整客户小程序 当前最大问题是内部交易和账务闭环，不是客户自助入口。 内部主链路稳定，复购频率足够高。
完整微信/支付宝支付接口 第一版先验证付款归账逻辑，避免支付接入拖慢 MVP。 付款请求单、收款分配、预付款流水已稳定。
微服务 订单、付款、预付款核销需要强一致事务；团队和订单量暂不需要微服务。 团队扩大且模块边界由真实数据验证。
复杂 BI 大屏 第一版运营需要今日待办和每日复盘，不需要展示型大屏。 数据稳定后再做经营分析扩展。

2. AI 执行入口

任何 AI 接手实施前，必须先读取这些上下文。不要直接开写代码。

顺序 文件 读取目的
1 03_系统侧支持地图.md 理解系统到底支持哪些业务动作。
2 04_系统用户操作流程梳理.md 理解用户在系统中的操作路径。
3 05_客户付款解决方案.md 理解付款请求、收款归账和预付款核销。
4 02_规模化技术赋能路线.md 理解技术栈、模块边界和 30 天路线。
5 本计划书 按任务卡执行开发、验收和交接。

AI 接手硬规则

  • 每次只推进一个阶段，不要同时做原型、后端、支付接口和部署。
  • 任何功能都必须围绕主链路，不服务主链路的功能后置。
  • 涉及金额的字段统一使用定点金额，不使用浮点数。
  • 状态变更必须有日志，付款和预付款必须有流水。
  • 每阶段结束必须输出交付物、运行方式、测试结果和下一步风险。

3. 总体架构

React/Next.js运营台、客户轻量页、供应商确认页
NestJS API模块化单体后端
业务服务层客户、订单、付款、供应商、看板
阿里云 MySQL核心交易与账务数据

模块边界

模块 职责 核心交付物
客户模块 客户身份、联系方式、地址、忌口、来源、状态、时间线。 客户列表、客户详情、客户时间线、客户标签。
订单模块 创建订单、订单状态、订单成本、订单毛利、售后。 订单工作台、订单详情、状态日志、售后记录。
支付账务模块 付款请求、实际收款、收款分配、预付款充值/核销/退款。 收款管理、预付款账户、每日对账异常。
供应商履约模块 供应商、供应商餐品、下单批次、供应商确认、异常反馈。 供应商批次页、复制下单文本、确认状态。
经营看板模块 今日待办、实收、营业额、预收款、成本、毛利、异常。 今日运营台、每日经营摘要。
配置模块 套餐、价格、供应商成本、配送规则、操作用户。 配置中心、基础数据维护页。

4. 阶段路线

阶段 0：项目准备

目标：锁定技术栈、目录结构、环境变量和执行规范。

交付：仓库骨架、README、环境模板、任务看板。

阶段 1：可运行原型

目标：用 mock 数据跑通主链路和关键页面。

交付：React 原型、页面流、交互说明。

阶段 2：数据库与后端骨架

目标：建立 NestJS + Prisma + MySQL 的基础工程。

交付：schema、迁移、模块目录、健康检查 API。

阶段 3：核心业务闭环

目标：客户、订单、付款、预付款、供应商批次可真实保存。

交付：CRUD、状态流转、付款请求、核销流水。

阶段 4：经营与异常

目标：运营每天能处理待办和复盘。

交付：今日运营台、每日经营看板、异常池。

阶段 5：试运行与上线

目标：用真实业务跑 7 天，修正流程并部署。

交付：部署环境、测试报告、操作手册、上线清单。

ID 交付物 归属阶段 验收标准

D02 可运行 React 原型 阶段 1 能用 mock 数据完成新建客户、创建订单、确认收款、预付款核销、生成供应商批次。
D03 数据库 schema 与迁移脚本 阶段 2 包含客户、订单、付款、预付款、供应商批次、日志、异常表。
D04 NestJS 模块化后端 阶段 2 模块边界清晰，具备基础 API、错误处理、配置管理和健康检查。
D05 客户与订单真实 CRUD 阶段 3 前端能真实创建、编辑、查询客户和订单，并写入 MySQL。
D06 付款请求与预付款核销 阶段 3 订单款、预付款充值、余额核销、退款和异常款可被准确记录。
D07 供应商批次与下单文本 阶段 3 能按日期和供应商生成批次，复制标准下单文本并回写状态。
D08 今日运营台与经营看板 阶段 4 能显示待办、异常、实收、营业额、预收款、成本和毛利。
D09 测试套件与试运行报告 阶段 5 关键链路有自动化测试；真实试跑 7 天后有问题清单和修复记录。
D10 部署包与操作手册 阶段 5 能在目标环境启动；运营可按手册完成日常操作。

6. AI 可执行任务卡

T00 · 项目初始化 阶段 0

输入：本计划书、现有业务文档、技术栈约束。

动作：创建应用目录、初始化前端和后端工程、配置 TypeScript、lint、环境变量模板。

交付物：apps/web、apps/api、README.md、.env.example。

验收：本地能启动前端和后端；README 写清启动命令。

T01 · React 可运行原型 阶段 1

输入：系统用户操作流程、客户付款方案。

动作：用 mock 数据实现今日运营台、客户详情、订单工作台、收款核销、供应商批次、经营看板。

交付物：可点击前端原型、mock 数据、页面流说明。

验收：无需数据库即可完整模拟“客户 → 订单 → 付款 → 批次 → 复盘”。

T02 · MySQL schema 与 Prisma 阶段 2

输入：数据表清单、付款方案、模块关系说明。

动作：设计 Prisma schema，创建迁移，建立金额、状态、日志和索引规范。

交付物：schema.prisma、迁移文件、种子数据、ERD 说明。

验收：数据库能迁移成功；关键表具备审计字段、状态字段和索引。

T03 · 客户模块 阶段 3

动作：实现客户创建、编辑、查询、地址、偏好、来源、状态、时间线。

交付物：客户 API、客户页面、客户详情页、客户时间线。

验收：创建客户后，订单创建能自动带出地址、忌口、余额和联系方式。

T04 · 订单模块 阶段 3

动作：实现订单创建、订单明细、成本拆分、状态流转、售后入口。

交付物：订单 API、订单工作台、订单状态日志。

验收：订单状态可从待付款流转到已付款待下单、已下发供应商、已完成或售后。

T05 · 付款与预付款模块 阶段 3

动作：实现付款请求、收款确认、收款分配、预付款充值、余额核销、退款、异常款。

交付物：付款 API、收款管理页、预付款账户页、每日对账异常。

验收：预付款充值不计入营业额；余额核销后对应订单收入；退款影响毛利。

T06 · 供应商履约模块 阶段 3

动作：实现供应商、供应商餐品、下单批次、复制微信文本、确认和异常。

交付物：供应商 API、批次页面、下单文本模板。

验收：已付款订单能按日期和供应商生成批次，并回写订单状态。

T07 · 今日运营台与看板 阶段 4

动作：聚合待办、异常、今日核心数据和快捷操作。

交付物：首页运营台、经营看板 API、每日摘要。

验收：运营能通过首页知道当天所有未处理事项和账务异常。

T08 · 试运行与修正 阶段 5

动作：导入真实业务样例，连续试跑 7 天，记录问题并修正。

交付物：试运行报告、问题清单、修复记录、操作手册。

验收：7 天内订单、付款、预付款和供应商批次都能闭环，异常可追踪。

8. 原型与页面计划

页面 第一版必须支持的动作 后置增强
今日运营台 查看待报价、待付款、待下单、供应商未确认、收款未关联、售后异常。 消息提醒、今日摘要推送。
客户详情 查看地址、忌口、余额、历史订单、时间线。 客户画像、复购建议。
订单工作台 创建订单、查看毛利、流转状态、进入售后。 批量改状态、订单复制。
收款管理 发起付款请求、确认收款、处理异常款。 支付接口回调、收款流水导入。
预付款账户 充值、核销、退款、查看流水。 客户自助余额查询。
供应商批次 按日期/供应商生成批次、复制下单文本、标记确认。 供应商确认页。
经营看板 实收、营业额、预收款、核销、退款、成本、毛利、异常。 套餐、供应商、区域、来源分析。

9. 测试与验收

关键测试场景

  1. 新客户创建后，能创建订单并自动带出客户地址和忌口。
  2. 订单收款确认后，订单状态变为已付款待下单。
  3. 预付款充值后，客户余额增加但营业额不增加。
  4. 余额下单后，预付款流水扣减，订单收入增加。
  5. 供应商批次生成后，订单进入已下发供应商。
  6. 供应商确认后，批次和订单状态同步更新。
  7. 退款后，订单毛利和每日经营数据正确变化。
  8. 每日看板能发现未关联收款、未确认批次和负毛利订单。

验收口径

类别 验收标准
业务闭环 一笔真实订单能从客户创建走到每日复盘。
账务闭环 订单款、预付款、核销、退款均有流水和归属。
运营效率 供应商下单文本由系统生成，无需二次整理。
可追溯 订单状态、付款、预付款、退款和售后均可追溯。
可交接 README、操作手册、部署说明和测试结果完整。

10. 部署与运营计划

环境

环境 用途 要求
本地开发 开发和单元测试。 本地可用 mock 或测试 MySQL。
测试环境 试运行真实流程。 与生产隔离，保留测试数据。
生产环境 真实运营使用。 连接阿里云 MySQL，开启备份，限制公网访问。

上线前清单

  • 环境变量全部配置完成，敏感信息不入库、不入 Git。
  • MySQL 开启备份，确认恢复方式。
  • 管理员账号创建完成。
  • 至少导入 5 个测试客户、5 笔订单、3 种付款场景。
  • 运营手册覆盖新客户、付款、建单、供应商批次、每日复盘。
  • 关键异常有处理方式：未关联收款、余额不足、退款、供应商异常。

11. 风险与关键决策

风险 表现 应对
过早接支付接口 MVP 迟迟做不完，账务模型还没验证。 先做付款请求单和人工确认，后续再接官方支付。
字段设计过重 运营录一单很慢，反而不用系统。 第一版只保留主链路字段，其他作为备注或后置。
只做页面不做流水 看起来有系统，但账依然不可追溯。 所有付款、核销、退款、状态变化必须写日志。
看板先行 报表漂亮但没有真实数据基础。 先客户、订单、付款、批次，再做经营看板。
供应商协作过重 供应商不愿登录复杂后台。 先复制文本，后续只给轻量确认页。

- 环境变量
- 测试命令

【验收结果】

- 未通过或未覆盖的场景

- 问题 2
