# 知识提炼 · 健康餐业务运营

> 从健康餐业务运营研究过程中提炼的核心结论与知识点，持续更新。

## 2026-06-07 · 中台维护文档与数据库口径

**核心观点**：
- 交易运营中台 MVP 的维护材料必须分成“服务启停”和“数据库口径”两类，前者保证能跑、能停、能查健康，后者保证运营指标、预付款、退款和供应商批次不会被误解。
- 服务维护口径应明确本机 `.env.local` 的端口优先级、默认端口回退、API 健康检查、只停止本项目 Node 进程，以及 MySQL 模式切换方式。
- 数据库维护口径应明确 memory 与 MySQL 双模式、核心表职责、订单/付款/预付款/批次状态、看板指标公式、日期时区处理和 MVP 与正式财务系统的边界。
- 自动化测试暴露出一个时间排序脆弱点：测试不能假设新建付款请求一定排第一，应按业务特征定位本次数据，避免种子时间和当前时钟相对关系导致测试不稳定。

**关键框架/模型**：
- 维护文档拆分：`01_服务启停维护.md` 覆盖启动、停止、重启、健康检查、MySQL 模式和排障；`02_数据库口径解读.md` 覆盖建库建表、表职责、状态流转、指标、异常和维护边界。
- 验收闭环：新增维护文档后仍需执行 `npm run build`、`npm test`、`npm run lint`、`npm audit --audit-level=moderate`，并对失败测试继续返工。
- 运行环境口径：`.env.example` 只能给默认 memory 口径和 MySQL 切换提示，不能同时声明两次 `DATA_STORE`。

**与其他话题的关联**：
- → 交易运营中台 MVP 开发落地：维护文档是可运行 MVP 的交接材料，保证后续接手者能启动、停止、联库和核对指标。
- → 客户付款解决方案：数据库口径把预付款充值、余额核销、订单收入和退款的边界沉淀为维护规则。
- → 模块关系与 MySQL 选型：MySQL 表职责和日期读取口径继续服务于模块化单体 + 阿里云 MySQL 的技术路线。

## 2026-06-07 · 交易运营中台 MVP 开发落地

**核心观点**：
- 健康餐交易运营中台的第一版应直接做“能跑主链路”的运营工具，而不是继续停留在静态计划书或页面说明。
- 本次落地采用 React + Vite 前端、Express API、MySQL schema/迁移和内存演示模式的组合，既能快速本地验收，也能接入用户已有阿里云 MySQL。
- 主 agent 与 subagent 框架在实际开发中应体现为：subagent 只读审阅框架与功能缺口，主 agent 负责实现、冲突处理、测试、返工和最终验收结论。
- 远程 MySQL 验收要同时检查 TCP 连通、迁移种子、store 读数和日期口径；MySQL `DATE` 经 JavaScript Date 转换时需避免 UTC 截断导致服务日期退一天。

**关键框架/模型**：
- MVP 功能闭环：客户详情/新建客户、订单工作台、新建订单、付款请求、确认收款、预付款充值与核销、供应商批次、复制下单文本、供应商确认、每日复盘。
- 数据层双模式：`DATA_STORE=memory` 用于稳定演示和自动化测试；`DATA_STORE=mysql` 连接远程 RDS，使用 `db:seed` 创建数据库、核心表和种子数据。
- 验收闭环：`npm run build`、`npm test`、`npm run lint`、`npm audit --audit-level=moderate`、MySQL 迁移种子、MySQL store 读数、Browser 桌面/移动端截图和交互验证。
- 安全口径：真实数据库密码只作为运行时环境变量使用，不写入 HTML、源码或 README；`.env.local` 只放非敏感端口/API base 配置。

**与其他话题的关联**：
- → 开发实施计划书：本次把计划书中的 T01/T02/T03-T07 压缩落地为一个可运行 MVP 工程。
- → 客户付款解决方案：付款请求、人工确认收款、预付款充值和余额核销已进入代码实现与测试。
- → 模块关系与 MySQL 选型：模块化单体 + 阿里云 MySQL 的方向经迁移种子和 store 读数验证可行。

## 2026-06-07 · 开发实施计划书

**核心观点**：
- 健康餐交易运营中台开发应按“可运行原型 → 数据库与后端骨架 → 核心业务闭环 → 经营异常 → 试运行上线”推进。
- 任意 AI 接手前必须先读系统侧支持地图、用户操作流程、客户付款方案、规模化技术路线和本计划书。
- 第一版交付重点不是完整客户小程序，而是内部运营主链路、付款归账、供应商批次和每日复盘。
- 每阶段都必须输出交付物、验收标准、测试结果和交接模板，避免 AI 接手断层。

**关键框架/模型**：
- 阶段路线：项目准备、可运行原型、数据库与后端骨架、核心业务闭环、经营与异常、试运行上线。
- 交付物：产品主链路说明、React 原型、MySQL schema、NestJS 后端、客户/订单 CRUD、付款与预付款、供应商批次、经营看板、测试报告、部署包与操作手册。
- AI 任务卡：T00 项目初始化、T01 React 原型、T02 MySQL schema 与 Prisma、T03 客户模块、T04 订单模块、T05 付款与预付款、T06 供应商履约、T07 今日运营台与看板、T08 试运行与修正。

**与其他话题的关联**：
- → 产品原型：计划书中的 T01 可直接作为 React 原型开发入口。
- → 系统开发：后续开发应从 D03/T02 的数据模型与 D05-D08 的主链路模块开始。

## 2026-06-07 · 客户付款解决方案

**核心观点**：
- 客户付款问题不能只理解为“用微信还是支付宝”，核心是系统如何让钱和订单、预付款、退款、对账准确关联。
- 第一版不急着接完整支付接口，应先做“付款请求单 + 客户付款 + 运营确认 + 系统归账”的半自动流程。
- 预付款充值不能直接算营业额，只有核销到具体订单时才转为订单收入。
- 后续再逐步升级为商户码与流水匹配、微信支付/支付宝官方接口自动回调。

**关键框架/模型**：
- 支付相关表：`payment_requests`、`payments`、`payment_allocations`、`prepaid_accounts`、`prepaid_ledger`、`refunds`、`reconciliation_issues`。
- 付款场景：单餐付款、预付款充值、余额下单、补差价、退款。
- 路线：半自动收款 → 商户码与流水匹配 → 官方支付接口。

**与其他话题的关联**：
- → 系统用户操作流程：客户付款是“记录收款 → 创建订单/充值余额 → 进入待下单”的核心节点。
- → 系统开发：第一版数据库和接口应优先支持付款请求、收款分配、预付款流水和每日对账异常。

## 2026-06-07 · 系统用户操作流程

**核心观点**：
- 第一版最重要的系统用户是运营，管理员、客户和供应商先作为辅助角色或轻量页面存在。
- 系统操作的核心不是录很多表，而是让“客户进来 → 报价跟进 → 付款归类 → 创建订单 → 供应商批次 → 完成售后 → 每日复盘”形成闭环。
- 首页应是今日运营台，而不是报表大屏；运营每天先处理待报价、待付款、待下单、供应商未确认、收款未关联和售后异常。
- 第一版要避免操作复杂度，遵循“能自动带出的不手填、能从订单推导出的不重复录、能一个页面完成的不要拆三步”。

**关键框架/模型**：
- 运营主流程：新客户进入系统、报价与跟进、客户付款、创建订单、生成供应商下单批次、供应商确认、完成/售后、每日复盘。
- 管理员配置：套餐餐品、供应商、配送规则。
- 外部轻量流程：客户确认页、余额查询页、复购入口、供应商确认页。
- 第一版页面清单：今日运营台、客户列表、客户详情、订单工作台、收款管理、预付款账户、供应商批次、经营看板、配置中心。

**与其他话题的关联**：
- → 产品原型：下一步可按这些页面和主链路直接做 React 可运行原型。
- → 系统开发：后续 API 和数据库表应优先支撑运营主流程，而不是先做外围能力。

## 2026-06-07 · 系统侧支持地图

**核心观点**：
- 系统不是为了替代微信聊天，而是把微信里承载的客户、订单、账务、履约、售后和复购转移成可管理事实。
- 系统的业务角色可以理解为调度台、账本、履约中枢和经营仪表盘。
- 系统侧最核心的支持是：看清楚、推得动、省动作、钱清楚、履约稳、能经营。
- 第一版应先跑通“客户 → 订单 → 收款/预付款 → 供应商下单 → 每日复盘”主链路。

**关键框架/模型**：
- 支持分层：记录事实 → 驱动流程 → 自动核算 → 外部协同 → 经营优化。
- 第一版关键场景：新客户、客户付款、供应商下单、预付款套餐、晚上复盘。
- 目标变化：微信只负责沟通，系统负责事实、流程、账务、履约和经营。

**与其他话题的关联**：
- → 产品原型：下一步原型可以直接围绕这 5 个关键场景画页面和交互。
- → 系统开发：后续数据库和接口优先围绕主链路设计，避免一开始做散乱功能。

## 2026-06-07 · 原型工具选择

**核心观点**：
- 健康餐交易运营中台不应只画静态原型图，最有价值的是可运行的 Web 原型。
- Excalidraw 适合画业务流、模块关系和页面流转；Figma 适合少量关键页面的视觉评审；HTML / React / Next.js 适合真正验证操作效率。
- 该项目的核心风险不是视觉，而是流程、状态和账务关系，因此可点击、可录单、可模拟收款核销和供应商批次的原型更适合。
- 第一份原型应优先覆盖今日运营台、订单工作台、客户详情、收款核销、供应商批次和经营看板。

**关键框架/模型**：
- 原型分层：Excalidraw 草图 → Figma/HTML 低保真 → React 可运行原型 → NestJS + 阿里云 MySQL MVP。
- 工具选择：业务结构用 Excalidraw，视觉沟通用 Figma，真实验证用 React/Next.js。

**与其他话题的关联**：
- → 产品原型：后续可直接进入 React 原型开发，而不是先制作大量静态设计稿。
- → 系统开发：React 原型确认流程后，可以逐步接入 NestJS 后端和阿里云 MySQL。

## 2026-06-06 · 规模化技术赋能路线

**核心观点**：
- 对技术角色而言，飞书或 Excel 只能作为临时运营辅助，不应作为规模化主线。
- 技术主线应是“内部交易核心 + 运营中台 + 自动化接口”，第一版面向内部使用，但底层为客户自助、供应商协同和配送优化预留扩展。
- 一步到位不是一次做完所有端，而是从第一天选对领域模型、状态机、账务流水、事件日志和权限边界。
- 第一阶段应优先建设订单核心、支付与预付款核心、供应商履约批次、今日待办和每日经营看板。

**关键框架/模型**：
- 核心领域：客户域、订单域、支付与账务域、供应商履约域、配送域。
- 推荐架构：Web 运营中台 + 后端 API + 阿里云 MySQL + 状态日志/审计日志/定时任务。
- 自动化路线：复制型自动化 → 提醒型自动化 → 半集成自动化 → 规模化协同。
- 30 天路线：交易核心、履约与对账、经营视图、外部协同雏形。

**与其他话题的关联**：
- → 产品原型：后续可直接进入 Web 运营中台的信息架构和界面原型。
- → 系统开发：后续可从数据库 schema、订单状态机和预付款核销逻辑开始编码。

## 2026-06-06 · 模块关系与 MySQL 选型

**核心观点**：
- 客户、订单、支付账务、供应商履约、配送和经营看板不是彼此独立的应用，而是一个模块化单体中的领域边界。
- 第一版应保持一个 Web 运营中台、一个后端应用、一个阿里云 MySQL 数据库，避免过早拆微服务。
- 订单是业务主轴：客户 → 订单 → 支付/预付款核销 → 供应商履约批次 → 配送记录 → 经营看板。
- 用户已有阿里云 MySQL，应优先复用现成资源；当前重点是事务、金额精度、状态日志、预付款流水和索引设计。

**关键框架/模型**：
- 模块关系：强业务关联、清晰代码边界、共享交易真相源。
- MySQL 设计要点：InnoDB、`DECIMAL` 金额、`VARCHAR` 状态、审计字段、状态日志、预付款流水、关键索引。
- 推荐技术栈：Next.js 前端 + NestJS 后端 + 阿里云 MySQL + Prisma，Redis 和 OSS 按需后置。

**与其他话题的关联**：
- → 系统开发：后续数据库 schema 应直接按 MySQL 设计，不再按 PostgreSQL 假设。
- → 架构演进：后续如需拆分，也应先从模块化单体积累稳定边界和真实订单规模。

## 2026-06-06 · 健康餐转单业务产品侧优先级

**核心观点**：
- 当前业务最先要解决的不是客户小程序，而是内部订单与账务真相源。
- 账糊的根因不是单纯没有记账，而是客户、订单、收款、预付款、供应商履约之间没有结构化关联。
- 在不知道单单毛利、预付款余额、待下单订单和履约异常前，盲目做量会把亏损和混乱放大。
- 产品侧的首要价值是把微信聊天中的离散动作变成可管理状态，并把每日履约动作批量化。

**关键框架/模型**：
- 五张基础表：客户表、订单表、收款表、预付款账户表、供应商下单表。
- 三类状态：客户状态、订单状态、收款状态。
- 四层问题：账单清楚、单单提效、经营分析、数据议价。
- 单单毛利公式：客户实收金额 - 小饭桌成本 - 配送成本 - 优惠/退款 - 单单人工处理成本。

**与其他话题的关联**：
- → 产品原型：后续可把五张表和四个每日视图做成单人运营台原型。
- → 数据经营：后续可基于订单与收款结构沉淀日报、毛利分析和供应商议价数据。
