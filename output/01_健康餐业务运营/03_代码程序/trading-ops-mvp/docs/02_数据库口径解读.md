# 数据库口径解读

> 适用于 `trading-ops-mvp` 的 MySQL 表结构、业务状态、看板指标和对账口径维护。

---

## 1. 数据模式

系统支持两种数据模式：

| 模式 | 配置 | 数据来源 | 适用场景 |
|------|------|----------|----------|
| 内存模式 | `DATA_STORE=memory` | `server/memoryStore.ts` + `server/data/seed.ts` | 演示、前端调试、快速验收 |
| MySQL 模式 | `DATA_STORE=mysql` | `server/mysqlStore.ts` + `server/db/schema.sql` | 数据库联调、接口流程验收 |

MySQL 连接串通过 `.env.local` 或 shell 环境变量提供：

```text
DATABASE_URL=mysql://USER:PASSWORD@HOST:3306/healthy_meal_ops_mvp
```

真实密码只从 `db_config.md` 临时读取并填入本地运行环境，不能写进源码、README 或维护文档。

---

## 2. 建库建表口径

迁移脚本：

```text
server/db/migrate.ts
```

表结构：

```text
server/db/schema.sql
```

执行命令：

```powershell
npm run db:migrate
```

会做三件事：

1. 从 `DATABASE_URL` 解析库名。
2. 如库不存在，创建 `healthy_meal_ops_mvp`。
3. 执行 `schema.sql` 创建核心表。

写入演示数据：

```powershell
npm run db:seed
```

`db:seed` 会额外写入供应商、商品/套餐、客户、订单、付款请求和预付款流水演示数据。演示业务日期来自 `server/data/seed.ts`，当前为 `2026-06-07`。

## 3. 核心表职责

| 表 | 职责 | 关键口径 |
|----|------|----------|
| `customers` | 客户主档 | 保存微信名、联系方式、地址、忌口、客户状态和当前预付款余额 |
| `suppliers` | 供应商主档 | 保存供应商名称、联系人、启停状态和备注；停用不影响历史订单和历史批次 |
| `products` | 商品/套餐配置 | 保存商品名称、分类、说明、售价、供应商成本、配送成本、默认供应商和启停状态 |
| `orders` | 订单主表 | 保存服务日期、餐品、供应商、售价、成本、配送费、毛利、订单状态和付款状态 |
| `order_status_logs` | 订单状态日志 | 记录订单从创建到付款、下发供应商、确认、完成、退款的状态变化 |
| `payment_requests` | 付款请求单 | 记录运营发起的订单收款、预付款充值、补差价等待确认收款事项 |
| `payments` | 实收实退流水 | 记录已确认的收款和退款，使用 `idempotency_key` 防重复入账 |
| `prepaid_ledger` | 预付款余额流水 | 记录充值、核销、退款、调整后的余额变化，使用 `idempotency_key` 防重复记账 |
| `supplier_batches` | 供应商下单批次 | 按供应商和服务日期生成下单文本，记录批次确认状态 |
| `supplier_batch_items` | 批次明细 | 记录批次内订单、客户、餐品、地址、备注和供应商成本 |

当前 schema 使用 `VARCHAR` 保存状态枚举，业务枚举约束由 TypeScript 类型和接口逻辑控制。

## 4. 状态口径

### 4.1 订单状态

| 状态 | 业务含义 |
|------|----------|
| `WAIT_PAY` | 已建订单，等待客户付款或运营确认收款 |
| `PAID_WAIT_SUPPLIER` | 已付款，等待生成供应商下单批次 |
| `SENT_TO_SUPPLIER` | 已生成供应商批次，等待供应商确认 |
| `SUPPLIER_CONFIRMED` | 供应商已确认可接单 |
| `COMPLETED` | 订单履约完成 |
| `AFTER_SALE` | 售后处理中，MVP 暂未完整展开 |
| `REFUNDED` | 已退款 |
| `CANCELED` | 已取消，MVP 暂未完整展开 |

### 4.2 付款请求类型

| 类型 | 业务含义 |
|------|----------|
| `ORDER_PAYMENT` | 订单收款 |
| `PREPAID_TOPUP` | 预付款充值 |
| `BALANCE_SHORTFALL` | 余额不足补差价，MVP 保留类型但暂未独立展开流程 |

付款请求状态：

- `WAIT_PAY`：待确认。
- `PAID`：已确认并写入 `payments`。
- `CANCELED`：已取消，取消后不能再确认收款。

### 4.3 支付与预付款流水类型

`payments.type`：

- `ORDER_PAYMENT`：订单实收。
- `PREPAID_TOPUP`：预付款充值实收。
- `REFUND`：退款，金额为负数。

`payments.status`：

- `POSTED`：已入账，参与现金流和退款统计。
- `VOIDED`：已作废，不再参与现金流统计。

`prepaid_ledger.type`：

- `TOPUP`：预付款充值，金额为正数。
- `DEDUCT`：余额核销订单，金额为负数。
- `REFUND`：预付款退回或恢复，MVP 暂未完整展开。
- `ADJUST`：人工调整；当前用于已确认预付款充值作废/冲正时回滚客户余额。

### 4.4 商品与供应商状态

商品和供应商都使用：

- `ACTIVE`：启用，可被新订单或新批次使用。
- `INACTIVE`：停用，保留历史记录，但不建议继续用于新业务。

### 4.5 供应商批次状态

| 状态 | 业务含义 |
|------|----------|
| `GENERATED` | 已生成但未发送，MVP 当前主要使用 `SENT` |
| `SENT` | 已生成下单文本并视为已下发供应商 |
| `CONFIRMED` | 供应商已确认 |

## 5. 核心流程口径

### 5.1 新建订单

- 如果不使用余额支付：订单进入 `WAIT_PAY`，同时生成 `ORDER_PAYMENT` 类型付款请求。
- 如果使用余额支付：先检查客户余额是否足够；足够时写入 `prepaid_ledger.DEDUCT`，订单进入 `PAID_WAIT_SUPPLIER`。
- 毛利初始计算：`amount - supplier_cost - delivery_cost`。

### 5.2 人工确认收款

- 根据付款请求写入 `payments`。
- 使用 `idempotency_key` 防止重复确认。
- 已取消的付款请求不能再确认。
- 订单收款确认后，订单状态进入 `PAID_WAIT_SUPPLIER`。
- 预付款充值确认后，客户余额增加，并写入 `prepaid_ledger.TOPUP`。

待付款请求可以取消或删除；已确认请求不能删除。

### 5.3 生成供应商批次

- 只会选择同一供应商、同一服务日期、状态为 `PAID_WAIT_SUPPLIER` 的订单。
- 生成批次后，订单状态从 `PAID_WAIT_SUPPLIER` 改为 `SENT_TO_SUPPLIER`。
- 批次明细使用 `supplier_batch_items` 保存，订单和批次之间通过 `order_id` 关联。

### 5.4 供应商确认与完成

- 确认批次后，批次状态为 `CONFIRMED`。
- 批次内订单状态变为 `SUPPLIER_CONFIRMED`。
- 只有 `SUPPLIER_CONFIRMED` 订单可以被标记为 `COMPLETED`。

### 5.5 退款

- 退款写入 `payments`，类型为 `REFUND`，金额为负数。
- 订单 `payment_status` 和 `status` 变为 `REFUNDED`。
- 当前实现会把退款金额从订单 `gross_profit` 中扣减。
- MVP 版暂未把订单付款退款和预付款余额恢复做成完整会计分录，正式生产前需要补充更细的退款归属规则。

### 5.6 充值作废/冲正

- 已确认的预付款充值不能硬删除。
- 作废时将 `payments.status` 改为 `VOIDED`，记录 `voided_at` 和 `void_reason`。
- 如果客户余额足够回滚，系统会扣减客户余额，并写入一条 `prepaid_ledger.ADJUST` 负向流水。
- 如果充值金额已经被后续订单核销，当前 MVP 会阻止直接作废，避免余额和流水不一致。

## 6. 看板指标口径

所有看板指标以业务日期 `today` 为核心过滤条件。当前演示业务日期是：

```text
2026-06-07
```

| 指标 | 计算口径 |
|------|----------|
| `orderCount` | 服务日期等于 `today` 的订单数 |
| `waitPayCount` | 今日订单中 `status = WAIT_PAY` 的数量 |
| `waitSupplierCount` | 今日订单中 `status = PAID_WAIT_SUPPLIER` 的数量 |
| `unconfirmedBatchCount` | `supplier_batches.status != CONFIRMED` 的批次数 |
| `revenue` | 今日已付款或已退款订单售价合计 - 今日退款金额 |
| `cashIn` | 今日 `payments.status = POSTED` 且 `payments.amount > 0` 的实收金额合计 |
| `prepaidTopup` | 今日 `prepaid_ledger.type = TOPUP` 的金额合计，并叠加 `ADJUST` 调整金额 |
| `prepaidDeducted` | 今日 `prepaid_ledger.type = DEDUCT` 的绝对值合计 |
| `refund` | 今日 `payments.type = REFUND` 的绝对值合计 |
| `supplierCost` | 今日已付款或已退款订单的供应商成本合计 |
| `deliveryCost` | 今日已付款或已退款订单的配送成本合计 |
| `grossProfit` | 今日已付款或已退款订单的毛利合计 |
| `issueCount` | 未解决异常数量 |

注意：

- `cashIn` 是当天实际确认的现金流入。
- `revenue` 是订单收入口径，和 `cashIn` 不一定一致。
- 预付款充值进入 `cashIn` 和 `prepaidTopup`，不直接等同于订单收入。
- 余额核销进入 `prepaidDeducted`，订单收入只按订单维度统计一次，避免重复算收入。
- 已作废充值不再进入 `cashIn`，并通过 `ADJUST` 抵减预收款口径。

## 7. 异常池口径

异常池由当前订单和批次状态实时计算：

| 异常类型 | 触发条件 | 等级 |
|----------|----------|------|
| `WAIT_PAY` | 订单状态为 `WAIT_PAY` | `MEDIUM` |
| `NEGATIVE_MARGIN` | 订单毛利小于 0 | `HIGH` |
| `BATCH_UNCONFIRMED` | 供应商批次未确认 | `HIGH` |

MVP 中异常为实时派生结果，暂未做人工关闭、处理记录和责任人分配。

## 8. 日期与时区口径

当前演示数据使用固定业务日期 `2026-06-07`。

内存模式：

- `nowIso()` 默认使用 `BUSINESS_DATE`。
- 未设置 `BUSINESS_DATE` 时默认 `2026-06-07`。
- 新增数据会拼接当前时钟时间，形成同一业务日内的 ISO 时间。

MySQL 模式：

- `orders.service_date` 和 `supplier_batches.service_date` 是 MySQL `DATE` 类型。
- 读取 MySQL `DATE` 时必须按本地 `getFullYear()`、`getMonth()`、`getDate()` 组装日期。
- 不要使用 `toISOString().slice(0, 10)` 处理 MySQL `DATE`，否则在时区转换时可能出现日期回退。

## 9. 数据质量约束

当前已落地的约束：

- `payments.idempotency_key` 唯一，防止重复收款或重复退款。
- `prepaid_ledger.idempotency_key` 唯一，防止重复余额流水。
- `supplier_batch_items.order_id` 唯一，防止同一订单进入多个供应商批次。
- 订单、客户、商品、供应商、付款请求、收款流水、批次均有常用查询索引。

当前未落地但生产前建议补充：

- 外键约束或应用层一致性扫描。
- 售后状态和售后原因表。
- 预付款账户独立表。
- 收款分摊表，例如一笔付款拆到多个订单。
- 供应商结算表和成本调整流水。
- 操作人、权限、审计日志。

## 10. 维护边界

这版数据库是交易运营中台 MVP 口径，目标是跑通客户、订单、收款、预付款、供应商下单和每日复盘闭环。

不能直接把它视为完整财务系统：

- 预付款目前是运营核算口径，不是正式会计凭证。
- 退款目前只覆盖订单退款的 MVP 流程，不覆盖部分退款、原路退回、预付款退回和多订单分摊。
- 已确认充值作废只覆盖余额足够回滚的场景；余额已被核销时需要后续补更完整的冲正审批和分摊逻辑。
- 收款目前是人工确认，不是微信、支付宝或银行回调。
- 所有生产财务口径上线前，需要由业务负责人和财务口径再确认。
