# 主 agent 与 subagent 协作框架方案

> 状态：方案文档，本轮不执行  
> 首次落盘：2026-06-07  
> 适用范围：后续开发、测试、代码审查、文档整理等 AI 协作任务  

---

## 一、目标

建立一套“主 agent 负责统筹与验收，subagent 负责具体执行”的协作框架。主 agent 不再把所有事情都压在单次对话里完成，而是把任务拆成有边界、有输入、有交付物、有验收标准的执行单元，再分发给不同 subagent。

这个框架的核心目标有四个：

1. 让主 agent 保持全局视角，负责需求澄清、方案拆解、任务编排、冲突处理和最终验收。
2. 让 subagent 专注单一执行任务，例如开发、测试、代码审查、文档补齐、数据验证。
3. 让每个任务都能被恢复、复查和返工，而不是依赖上下文记忆。
4. 让最终交付由主 agent 统一确认，避免“开发者自测即验收”的质量失真。

本轮只沉淀框架方案，不启动真实 subagent，不创建开发任务队列，不修改现有入口规则或 Skill。

---

## 二、问题背景

单一 agent 同时承担产品理解、技术设计、代码实现、测试验证和最终验收时，容易出现三个问题。

第一，上下文会变得臃肿。agent 一边记业务目标，一边记实现细节，一边记测试反馈，越到后面越容易丢掉最初的验收标准。

第二，执行视角会污染验收视角。亲自写代码的 agent 往往更容易相信自己的实现，最终验收容易变成“我觉得已经完成”，而不是逐项对照用户目标和测试结果。

第三，复杂任务难以并行推进。开发、测试、文档、代码审查本可以分开执行，但单一 agent 往往只能串行推进，导致长任务中断后难恢复。

因此需要引入主 agent 与 subagent 的职责分离：主 agent 作为任务 owner 和验收人，subagent 作为短周期专业执行单元。

## 四、最终判断

这个框架不应该先从“启动多少个 subagent”开始，而应该先从“任务契约”开始。

主 agent 与 subagent 之间必须通过任务卡、上下文包、交付物清单和验收标准协作。只要这些契约清楚，即使当前环境暂时没有真正的并行 subagent，也可以先用手动分发、分阶段执行或多会话执行的方式落地。

主 agent 需要保留最终判断权。subagent 可以报告“已完成”“测试通过”“建议合并”，但不能替主 agent 宣告最终验收通过。

subagent 的工作必须产物化。每个 subagent 结束时都要交付代码变更、测试结果、风险说明、未完成项和下一步建议，不能只交一段自然语言总结。

## 五、角色分工

| 角色 | 核心职责 | 可以决定 | 不可以决定 |
|---|---|---|---|
| 主 agent | 需求澄清、架构判断、任务拆分、调度、冲突处理、最终验收 | 任务优先级、依赖关系、是否返工、是否交付 | 不应把最终验收权下放给 subagent |
| 开发 subagent | 按任务卡实现功能、修复缺陷、补齐代码 | 局部实现方式、局部重构、单元测试补充 | 不得扩大需求范围，不得改无关文件 |
| 测试 subagent | 根据验收标准设计测试、执行测试、报告缺陷 | 测试用例、测试数据、缺陷分级建议 | 不得直接修改产品需求，不得替代验收 |
| 审查 subagent | 做代码审查、风险扫描、边界条件检查 | 风险判断、返工建议、缺测建议 | 不得自行合并或覆盖开发结果 |
| 文档 subagent | 整理说明、接口文档、交接文档、变更记录 | 文档结构、表达方式、缺口提示 | 不得改变系统真实行为 |
| 集成 subagent | 处理合并冲突、依赖整合、构建配置 | 集成细节、冲突修复建议 | 不得绕过主 agent 的质量门 |

最小可用配置可以只有三个角色：主 agent、开发 subagent、测试 subagent。审查、文档、集成可以在复杂度上升后再拆出来。

## 六、运行对象

这个框架围绕六类对象运转。

| 对象 | 说明 | 负责人 |
|---|---|---|
| 用户目标 | 用户真正想完成的业务或技术结果 | 主 agent |
| 任务图 | 把目标拆成可执行任务，并标明依赖关系 | 主 agent |
| 任务卡 | 分发给 subagent 的最小执行契约 | 主 agent 创建，subagent 执行 |
| 上下文包 | subagent 执行所需的规则、文件、背景和限制 | 主 agent |
| 交付包 | subagent 完成后返回的变更、测试、风险和未完成项 | subagent |
| 验收报告 | 主 agent 汇总所有任务后给出的最终判断 | 主 agent |

其中任务卡是最重要的对象。没有任务卡，就不要启动 subagent。

## 七、任务生命周期

建议使用如下生命周期管理所有开发和测试任务。

| 阶段 | 状态 | 主 agent 动作 | subagent 动作 |
|---|---|---|---|
| 需求进入 | `INTAKE` | 澄清目标、边界、成功标准 | 不参与 |
| 方案拆解 | `PLANNING` | 拆任务图、定义依赖、确认质量门 | 不参与 |
| 待分发 | `READY` | 生成任务卡和上下文包 | 不参与 |
| 执行中 | `RUNNING` | 监控进度、处理阻塞 | 按任务卡执行 |
| 待审查 | `REVIEW` | 检查交付包、决定是否返工 | 响应问题 |
| 待集成 | `INTEGRATION` | 合并结果、处理冲突 | 按需修正 |
| 待测试 | `TESTING` | 分发测试任务、收集结果 | 测试 subagent 执行 |
| 待验收 | `ACCEPTANCE` | 对照成功标准最终判断 | 不参与或只答疑 |
| 完成 | `DONE` | 向用户交付摘要和产物路径 | 不参与 |
| 返工 | `REWORK` | 重新开任务卡或补充上下文 | 按新任务卡执行 |

任务状态不能只靠聊天描述维护。后续真正执行时，建议每个任务都写入可恢复的任务进度文件或任务看板。

## 八、任务分发模型

主 agent 分发任务前，需要先把用户目标拆成任务图。任务图是一个有向无环图：先做基础能力，再做依赖它的功能，再做测试和验收。

任务拆分原则：

1. 一个任务只交付一个清晰结果。
2. 一个任务必须有可验证的完成标准。
3. 一个任务的读写文件范围要尽量小。
4. 不能把“开发 + 全量测试 + 文档 + 验收”塞进同一个 subagent。
5. 会互相修改同一批文件的任务默认串行，除非主 agent 能明确处理冲突。

任务卡建议使用以下结构。

```markdown
# 任务卡 · {任务编号} · {任务标题}

## 目标
用一段话说明本任务完成后系统应具备什么能力。

## 背景
说明为什么要做、上游任务结果是什么、用户目标是什么。

## 输入
- 需要阅读的文件：
- 可以参考的文档：
- 上游交付物：

## 允许修改范围
- 可以修改：
- 不得修改：

## 交付物
- 代码：
- 测试：
- 文档：
- 运行结果：

## 验收标准
- 功能标准：
- 测试标准：
- 兼容性标准：
- 风险标准：

## 执行约束
- 必须遵守的工作区规则：
- 必须保留的用户既有改动：
- 禁止事项：

## 返回格式
- 改了什么：
- 如何验证：
- 风险与未完成项：
- 建议下一步：
```

任务卡越清楚，subagent 越不需要猜。

## 九、上下文包设计

上下文包不是把所有文件都塞给 subagent，而是给它完成任务所需的最小事实。

建议上下文包包含六部分。

| 部分 | 内容 |
|---|---|
| 业务背景 | 用户目标、业务约束、关键术语 |
| 技术背景 | 当前架构、相关模块、依赖关系 |
| 工作区规则 | 必须遵守的读取、备份、测试、记忆规则 |
| 任务边界 | 允许读写的文件、禁止触碰的区域 |
| 验收标准 | 主 agent 后续会如何判断完成 |
| 风险提示 | 已知坑、并发冲突、历史决策 |

上下文包应该由主 agent 维护。subagent 可以要求补充上下文，但不能自行扩大任务边界。

## 十、主 agent 工作流

主 agent 的标准工作流如下。

1. 读取用户目标，判断是需求、修复、研究、测试还是发布。
2. 执行必要的工作区检查，确认规则、目录、当前变更状态。
3. 把目标拆成任务图，识别哪些可以并行，哪些必须串行。
4. 为每个任务生成任务卡和上下文包。
5. 按依赖顺序分发给 subagent。
6. 收集 subagent 交付包，检查是否符合任务卡。
7. 对不合格任务发起返工，不直接替 subagent 粉饰结果。
8. 将开发结果交给测试 subagent 或由主 agent 运行测试。
9. 统一做最终验收，给出是否完成、剩余风险和产物路径。
10. 写入任务进度、目录、版本记录和记忆。

主 agent 的重点不是亲自做最多的事，而是让每个执行动作都有边界、有证据、有验收。

## 十一、开发 subagent 协议

开发 subagent 只围绕任务卡工作。

开发 subagent 执行步骤：

1. 复述任务目标和允许修改范围。
2. 阅读任务卡列出的文件，不主动扩展到无关区域。
3. 给出局部实现计划。
4. 修改代码或文档。
5. 运行任务卡要求的测试或最小验证命令。
6. 返回交付包。

开发 subagent 返回格式：

```markdown
## 开发交付包

**任务编号**：
**完成状态**：完成 / 部分完成 / 阻塞

**改动文件**：
- ...

**实现说明**：
- ...

**验证结果**：
- 命令：
- 结果：

**风险与未完成项**：
- ...

**需要主 agent 决策**：
- ...
```

开发 subagent 不应自行做最终验收。如果任务卡不清楚，应先向主 agent 请求补充，而不是猜测用户意图。

---

## 十二、测试 subagent 协议

测试 subagent 的目标不是证明开发正确，而是尽量发现偏差。

测试 subagent 执行步骤：

1. 读取用户目标、验收标准和开发交付包。
2. 设计测试矩阵，覆盖正常路径、边界路径、异常路径和回归风险。
3. 执行自动化测试、手工验证或静态检查。
4. 把问题分为阻塞、严重、一般、建议。
5. 返回测试报告，明确是否建议进入主 agent 最终验收。

测试报告建议格式：

```markdown
## 测试报告

**测试范围**：
**测试结论**：建议通过 / 建议返工 / 阻塞

| 用例 | 类型 | 结果 | 证据 | 备注 |
|---|---|---|---|---|
| ... | 正常路径 | 通过 | ... | ... |

## 缺陷清单

| 严重级别 | 问题 | 复现方式 | 建议 |
|---|---|---|---|
| ... | ... | ... | ... |

## 剩余风险
- ...
```

测试 subagent 不能因为开发 subagent 自测通过就减少测试范围。

---

## 十三、审查与集成协议

当任务较大、修改文件较多或涉及核心模块时，应增加审查与集成步骤。

审查 subagent 重点看五类问题：

1. 是否偏离用户目标。
2. 是否改了无关文件。
3. 是否破坏既有接口或数据结构。
4. 是否缺少测试。
5. 是否引入安全、权限、金额、状态流转等高风险问题。

集成 subagent 重点处理四类问题：

1. 多个开发任务修改同一模块时的冲突。
2. 前后端接口字段不一致。
3. 数据库迁移与代码模型不一致。
4. 构建、依赖、环境变量和启动脚本不一致。

审查和集成只给建议或修复候选，最终是否接受由主 agent 判断。

## 十四、质量门

建议设置三道质量门。

### 1. 分发前质量门

主 agent 在分发任务前检查：

- 用户目标是否明确。
- 任务是否足够小。
- 允许修改范围是否清楚。
- 验收标准是否可检查。
- 是否存在未处理的依赖任务。

### 2. 合并前质量门

主 agent 在接受 subagent 交付包前检查：

- 是否按任务卡完成。
- 是否只修改允许范围内的文件。
- 是否有验证证据。
- 是否说明风险和未完成项。
- 是否需要测试 subagent 介入。

### 3. 最终验收质量门

主 agent 在向用户交付前检查：

- 用户原始目标是否满足。
- 所有阻塞级缺陷是否关闭。
- 必要测试是否运行并通过。
- 文档、目录、版本记录、记忆是否完成。
- 最终回复是否说明产物路径、验证结果和剩余风险。

主 agent 只有通过最终验收质量门后，才能说任务完成。

## 十五、并行与冲突处理

并行任务必须满足两个条件：没有强依赖关系，且写文件范围不重叠。

建议主 agent 在任务图中标注读写集合。

```text
任务 A：读 customer 模块，写 customer API
任务 B：读 order 模块，写 order API
任务 C：读 customer API 和 order API，写集成测试
```

上例中 A 和 B 可以并行，C 必须等 A 和 B 完成后再启动。

冲突处理原则：

1. 两个 subagent 修改同一文件时，主 agent 暂停合并，先判断谁的变更是主线。
2. 如果两个变更都合理，主 agent 创建集成任务，不让任一 subagent 自行覆盖对方结果。
3. 如果 subagent 超出任务边界，主 agent 可以拒收该交付包并要求返工。
4. 冲突解决后必须补测试，不能只解决文本冲突。

## 十六、主 agent 验收报告模板

主 agent 最终验收建议使用固定模板。

```markdown
## 最终验收报告

**用户目标**：
**验收结论**：通过 / 部分通过 / 未通过

## 已完成
- ...

## 产物路径
- ...

## 验证结果
- 命令：
- 结果：

## subagent 交付摘要
| 任务 | 角色 | 结论 | 风险 |
|---|---|---|---|
| ... | 开发 | 完成 | ... |

## 剩余风险
- ...

## 后续建议
- ...
```

验收报告由主 agent 编写，不由 subagent 代写。

## 十七、最小落地路线

建议分三阶段落地，不一开始就做复杂调度系统。

### 阶段 1：文档化调度

先用任务卡手动分发。主 agent 在当前对话或任务进度文件中维护任务图，subagent 可以是后续独立会话、人工执行者，或未来可用的多 agent 工具。

交付标准：

- 有任务图。
- 有任务卡。
- 有交付包。
- 有主 agent 验收报告。

### 阶段 2：半自动调度

把任务卡存成结构化文件，主 agent 维护任务状态。每个 subagent 按任务卡读取上下文、执行、写回交付包。

交付标准：

- 每个任务有状态。
- 每个任务有输入和输出。
- 返工任务可以追溯。
- 主 agent 可以从中断点恢复。

### 阶段 3：自动化调度

在工具条件允许时，再引入真正的 subagent 启动、排队、并行执行、日志收集和结果合并。

交付标准：

- 主 agent 能自动创建任务。
- subagent 能自动领取任务。
- 任务状态能自动更新。
- 测试和验收证据能自动回传。
- 主 agent 仍保留最终验收权。

## 十八、不做事项

本方案明确不做以下事项：

1. 不在本轮启动任何真实 subagent。
2. 不修改 `AGENTS.md`、`CLAUDE.md` 或 `.system/` 标准文件。
3. 不创建新的 Skill 或命令包装。
4. 不把本方案直接升级为工作区标准。
5. 不把开发、测试、验收全部交给同一个 subagent。
6. 不允许 subagent 自行扩大任务范围或覆盖用户已有改动。
7. 不用“subagent 已完成”替代主 agent 最终验收。

---

## 十九、后续真正执行时的启动清单

当用户后续要求“按这个框架执行开发”时，主 agent 应先完成以下清单。

1. 明确本次开发目标和不做范围。
2. 执行工作区强制门和必要体检。
3. 读取相关业务文档和代码现状。
4. 生成任务图。
5. 为第一批任务生成任务卡。
6. 判断哪些任务可以并行。
7. 分发开发任务。
8. 收集开发交付包。
9. 分发测试任务。
10. 汇总测试报告。
11. 主 agent 最终验收。
12. 写入版本记录、目录和记忆。

如果任何一步缺少输入，主 agent 应先补上下文，而不是直接让 subagent 开工。

---

## 二十、验收口径

这个协作框架是否可用，可以按以下标准验收：

| 验收项 | 可观察标准 |
|---|---|
| 职责清晰 | 主 agent 与各类 subagent 的职责和禁止事项已明确 |
| 任务可分发 | 有标准任务卡模板，subagent 拿到后能独立执行 |
| 过程可恢复 | 有任务生命周期和状态定义 |
| 质量可控 | 有分发前、合并前、最终验收三道质量门 |
| 测试独立 | 测试 subagent 与开发 subagent 职责分离 |
| 验收集中 | 最终验收权保留在主 agent |
| 可渐进落地 | 支持文档化、半自动和自动化三阶段演进 |

---

## 二十一、结论

主 agent 与 subagent 框架的关键不是“多几个 agent”，而是把协作变成契约化、产物化和可验收的流程。主 agent 负责方向、边界、调度和验收；subagent 负责具体执行；任务卡、上下文包、交付包和验收报告负责把双方连接起来。

后续真正进入开发时，可以先按“文档化调度”方式落地：主 agent 生成任务图和任务卡，开发 subagent 与测试 subagent 分别执行，最终由主 agent 统一验收。等任务量和工具条件成熟后，再升级为半自动或自动化调度。
